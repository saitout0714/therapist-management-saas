# キャスカン(Caskan) → yoyakl データ移行

新規案件でキャスカンを使っている店舗をyoyaklへ移行するとき、既存の顧客・セラピスト・ルーム・予約履歴を
`scripts/migrate-caskan.ts` で取り込むための手順。このスクリプトは既に汎用化されており、案件ごとに
コードを書き直す必要はない。手順を守らずに実行すると、対象は既に本番稼働中の店舗であることが多いため、
実データを壊したり重複させたりするリスクが高い。

## いつ使うか

- 新規案件で「キャスカンからのデータ移行」を頼まれたとき
- 既存案件で「もっと古いデータも取り込みたい」「期間を伸ばしてほしい」と言われたとき
- `lib/sync/caskan.ts` や `CASKAN_ROOM_MAP` を触る必要が出てきたとき（シフト同期機能と共有しているコードなので、変更する前に必ず本ファイルの「既知の落とし穴」を確認する）

対象店舗はコース料金・割引・バック金額の設定（`/system/edit`）が既にyoyakl側に手動登録されている前提。
これらの設定自体を移行することはスコープ外（今後もスコープ外にすること — 店舗ごとに個別カスタムが多く、
自動移行すると誤った料金体系を組んでしまうリスクの方が大きい）。

## 事前準備（対象店舗ごとに1回）

yoyakl側に以下が**先に**登録されていること。無ければ先にユーザーに確認する。

1. `shops` テーブルに対象店舗のレコード（store_id/shop_id の UUID を控えておく）
2. `courses` テーブルにコースが登録済み（コースはキャスカンの表示テキスト末尾の「◯◯分」からdurationで自動マッチするので、コース名は自由でよいが durationは正しく設定されている必要がある）
3. `designation_types` テーブルに指名種別が登録済み（free / first_nomination / confirmed が基本。この3種類が無い店舗の場合はマッピングの調整が必要になるので、実装前にユーザーと相談する）
4. （任意だが推奨）`rooms` テーブルにルームを事前登録。キャスカン側のルーム名と完全一致する名前で登録しておくと、`CASKAN_ROOM_MAP`が無くても自動でマッチする

キャスカンの管理画面を実際に開いて `/customer` `/cast` `/room` `/reserve` のHTML構造を確認したことがない
新しい種類の店舗（料金体系が大きく異なる、コース名の書式が「◯◯分」で終わらない等）の場合は、本番投入の前に
scratch配下で軽くHTMLを取得して構造を確認してから進める。

## 認証情報の渡し方

案件ごとにキャスカンのアカウント（shop_code / login_id / password）が異なることが多い。
**`.env.local` は書き換えない。** 環境変数の上書きでコマンド実行時にのみ渡す。こうすればパスワードが
シェル履歴やdotenvファイルに残らない。

```bash
CASKAN_SHOP_CODE=xxxx CASKAN_LOGIN_ID=yyyy CASKAN_PASSWORD=zzzz \
  npx tsx scripts/migrate-caskan.ts --caskan-shop-id=1234 --store-id=<yoyakl側shop_idのUUID> --shop-name=new_client
```

既に `lib/sync/caskan.ts` の `SHOPS` 配列に登録済みの店舗（同じキャスカンアカウントでshop_idだけ切り替える
既存店舗）であれば `--shop=<name>` で参照できる。

```bash
npx tsx scripts/migrate-caskan.ts --shop=rabbit_tachikawa
```

## 実行手順

**必ずこの順番で進める。dry run を飛ばして直接 `--commit` しない。**

1. **dry run を実行する**（`--commit` を付けない）。対象期間は明示的に指定する: `--date-to=YYYY-MM-DD`（通常は依頼のあった時点の「最新の営業日」まで）。`--date-from` を省略すると自動でキャスカン側の最古データまで遡る（内部で2010年から1年ずつ遡って探索し、2年連続でデータ0件になった時点で打ち切る仕組み）。
2. ログの最後に出る集計を**そのままユーザーに提示する**。省略したり要約しすぎたりしない。少なくとも次の数字は必ず伝える:
   - 顧客: 電話番号一致 / 名前一致(一意) / 名前重複で要確認 / 新規作成対象
   - セラピスト: 既存一致 / 新規作成対象(在籍+退店済み) / 削除済みタブで未マッチ(作成せず)
   - ルーム: マッピング成功(ID一致/名前一致) / 未登録
   - 予約: スクレイピング合計 / 顧客が特定できず本当にスキップ / 新規投入対象 / セラピスト未マッチ件数 / ルーム未マッチ件数 / コース未マッチ件数 / ステータス内訳
3. `null` になる項目（未マッチのセラピスト・ルーム等）や、要確認扱いになった重複名などは、その意味（下の「既知の落とし穴」参照）を説明した上でユーザーに「このまま進めてよいか」を確認する。件数が想定外に大きい場合（例: ルーム未マッチが投入対象の半分を超える等）は原因調査を優先し、先に進まない。
4. ユーザーの明示的な同意を得てから `--commit` を付けて再実行する。予約は `caskan_reservation_id` にUNIQUE制約があるため再実行しても重複投入されず安全（詳細は下記）。ただし顧客・セラピストの新規作成は、下記の落とし穴1のバグを踏むと重複作成されるので、**必ず落とし穴1のページネーション対策が効いていることを確認してから**本番実行する。
5. 実行後、簡単な検証を行う（下記「実行後の検証」）。

## 既知の落とし穴

このスクリプトを初めて実データに対して使ったとき、実際に以下の問題が起きて手動復旧が必要になった。
同じ轍を踏まないよう、コードを変更する前後で必ず頭に入れておくこと。

### 1. Supabaseの`.select()`はデフォルトで1000件までしか返らない

PostgRESTの `db-max-rows` 設定により、`.range()` を付けずに `.select()` すると先頭1000件で
黙って切られる。エラーにはならないので気づきにくい。

これが原因で、既存顧客が1000件を超える店舗では「既存チェック」が先頭1000件としか照合されず、
2回目の `--commit` 実行時に同じキャスカン顧客が再び「新規」と誤判定され、**顧客3088件が丸ごと
重複作成された**実績がある（`created_at`のタイムスタンプで2つのバッチに分かれて発覚し、
`name+phone+email+memo+status`の完全一致で1:1ペアリングして復旧した）。

`scripts/migrate-caskan.ts` の `fetchAllRows()` ヘルパーは対策済み。**このスクリプトや
`lib/sync/caskan.ts` に新しくSupabaseクエリを追加するときは、1店舗あたりの件数が1000件を
超える可能性があるテーブル（customers, reservations 等）は必ず `fetchAllRows()` と同じ
`.range()` ページネーションを使うこと。** 件数が少ないと分かっているテーブル（courses,
designation_types, rooms 等）は現状のまま単純な `.select()` でよい。

### 2. `CASKAN_ROOM_MAP` に、実在しないroom_idが混ざっていることがある

`lib/sync/caskan.ts` の `CASKAN_ROOM_MAP` はシフト同期機能と共有している、キャスカンの
room_id → yoyakl側 rooms.id のマッピング。店舗側で部屋を削除すると、このマップのエントリは
古いUUIDを指したまま残ってしまう。

このマップの値をそのまま`reservations.room_id`に使うと、実在しない部屋を参照するレコードを含む
バッチがFK制約違反で**バッチ全体（200件単位）が丸ごと失敗する**。実際に廃止済みの「立川（仮）」
という部屋のマッピングが原因で1,800件の予約投入が失敗したことがある。

本番投入前に、そのマップの値が実際に`rooms`テーブルに存在するか確認する。存在しなければ
マップから該当エントリを削除する（`room_id=null`にフォールバックする方が、存在しないIDを
指すよりずっと安全）。`scripts/migrate-caskan.ts`は既にID一致に加えて、対象店舗の`rooms`
テーブルとの名前一致もフォールバックとして試すようになっている（新規店舗はそもそも
`CASKAN_ROOM_MAP`にエントリが無いので、この名前一致が実質的な主経路になる）。

### 3. 予約日は年が表示されない

キャスカンの `/reserve` 一覧の「予約日」列は `7/20 月 26:10` のように年を含まない。
そのため `date_from`/`date_to` を**年単位**で区切ってクエリし、その年の範囲内でのみ
「M/D」を解釈することで年を一意に確定させている（月単位まで細かく区切る必要はない —
1年の範囲内であれば「7/20」が指す年は自明）。もし将来この解析ロジックを変更するなら、
年をまたぐ問い合わせを絶対にしないこと。

なお時刻が「26:10」のように24を超えるのは深夜営業の扱いで、そのままreservationsテーブルの
規約（`start_time`が24時以降になりうるテキスト値、その日の営業日扱い）に合致するので変換不要。

### 4. 顧客マッチングは「電話番号優先、名前は一意な場合のみ」

同姓の顧客が既存データに何件もあるのは普通（キャスカンも既存データも姓のみでフルネームや
生年月日を持たないことが多い）。名前だけで一致させようとすると、他人の予約履歴を誤って
別人の顧客レコードに紐付けてしまうリスクがある。それは重複作成より悪い（重複は後からマージ
できるが、誤帰属したデータは見た目上正常なので気づかれにくい）。

そのため: 電話番号が一致すればそれを使う。電話番号が無い/一致しない場合は、既存顧客の中で
その名前が**一意に**1件だけ存在する場合のみ使う。複数存在して確定できない場合は、安全側に
倒して新規作成する。この設計は変えないこと。

### 5. キャストは「在籍」「退店済み」タブのみ自動作成、「削除済み」タブは作成しない

キャスカンの `/cast?tab=1|2|3` は 1=在籍、2=退店済み、3=削除済み。削除済みタブには
「テスト」のような明らかなゴミデータが混ざっていることが確認されている。そのため
削除済みタブのキャストは既存セラピストとの名前一致のみ試し、一致しなければ
`therapist_id=null`のまま予約を投入する（新規セラピストとしては作成しない）。

もし削除済みタブに実在した元スタッフが多く含まれていて`therapist_id=null`の件数が
無視できないほど多い場合は、この方針を見直すかどうかユーザーに相談する
（例: 実際に予約から参照されている削除済みキャストだけは作成する、等の折衷案がありうる）。

### 6. 予約の冪等性と、顧客/セラピストの非冪等性は別物

`reservations.caskan_reservation_id` には部分UNIQUE制約（`WHERE caskan_reservation_id IS NOT NULL`）
があるため、スクリプトは既存の`caskan_reservation_id`集合を事前に取得してスキップする設計になっており、
**予約は再実行しても重複投入されない**。

一方、顧客・セラピストの新規作成には同様のUNIQUE制約による保護が無い。冪等性は完全にスクリプト側の
マッチングロジック（上記1・4・5）の正しさに依存している。落とし穴1のようなバグがあると静かに
重複が発生するので、顧客・セラピストの新規作成件数が「前回投入した件数と全く同じ」場合は
即座に疑うこと（実際の重複発生時、2回目の`--commit`のログは1回目と一字一句同じ「新規作成対象」件数を
出力していた）。

## 実行後の検証

投入が終わったら、必ず以下を確認してからユーザーに完了報告する。

1. 予約が存在しない顧客を参照していないか（orphaned reservations）:
   ```ts
   const validCustomerIds = new Set((await fetchAllCustomers()).map(c => c.id))
   const orphaned = reservations.filter(r => r.customer_id && !validCustomerIds.has(r.customer_id))
   // orphaned.length は必ず0であること
   ```
2. 投入した予約数が `caskan_reservation_id` のユニーク数と一致するか（重複投入されていないか）
3. 顧客・セラピストの最終件数が「移行前の件数 + 今回作成した件数」と一致するか（重複作成されていないか）
4. dry runで確認した未マッチ件数（セラピスト/ルーム/コース）が、実際の投入結果でも同程度の割合になっているか

ユーザーへの完了報告では、件数の差分（移行前→移行後）と、未マッチ・null許容にした項目を必ず明示する。
「だいたい移行できました」ではなく、具体的な件数と割合（例: 「予約は97.9%を投入、残りはキャスカン側で
顧客リンクが無い予約」）で伝える。

## 補足: 生の投入率だけでなく付随情報の充足率も伝える

「予約が何件投入できたか」と「投入した予約にセラピスト/ルームがちゃんと紐づいているか」は別の指標。
ユーザーに完了報告するときは両方を分けて伝える（例: 予約自体は97.9%投入できたが、ルームまで
紐づいているのは66%、のように）。
